# T17 durable event ingestion

`POST /api/events` is a public, cookie-free, versioned ingestion boundary. It validates our internal `ingestionBatch` contract and commits all accepted events before returning HTTP 202. It does not activate a Shopify pixel, prove event provenance or attribute a purchase. The earlier `/api/proof/events` and proof-only pixel remain separate feasibility prototypes; no synthetic traffic has been relabelled production.

Wire `storeId` means the public installation ID (`ShopInstallation.publicId`). The receiver resolves it to the internal store ID. Registered installed/uninstalled stores are recognised so delayed observations can arrive; pending/unregistered stores are rejected. This is not permission to enrol or serve after uninstall. Custom references must match the actual store, experiment, revision, variant and selected-ad mapping, with an experiment publication whose status is active or historically inactive and whose creation precedes the event. T27 must use inactive only for previously activated publications. Invented revisions/variants, cross-store references, unsupported versions and unexpected fields fail permanently.

Events are at most eight days old (seven-day outcome window plus one-day delivery grace), with at most five minutes of future clock skew. An ended experiment can receive events that occurred while it was enrolling; the check does not require a currently running experiment. Checkout events received after end are kept for T28/T29 matching/window enforcement. A custom event timestamp after its experiment end is rejected. This delivery bound does not itself decide attribution.

Assignment, rendering and failure remain distinct records. Assignment events carry a visitor ID; rendered events require an exposure ID. A render arriving before its assignment can be stored with the validated reference in its payload and a null relational assignment link; T19 must materialise/reconcile that link. No missing assignment or rendered exposure is fabricated. Standard checkout identifiers and amount may explicitly be null; T28 must quarantine/unmatch ambiguous identities and verify actual subtotal fields before generating revenue metrics.

Deduplication uses `(internal store, source, logical event ID)`: the stable app event ID for custom records and the Shopify event ID for standard records. Custom retry wrapper IDs can differ without creating a second event. A reused logical ID with changed content/client identity conflicts; it never silently overwrites a stored event. Purchase/order deduplication across *different* standard event IDs remains T28, not event deduplication.

Limits: 64 KiB per body, 1–20 events per batch, five-second body-read deadline and 600 submitted events per store per minute, enforced transactionally across workers. Duplicate submissions also consume the request's event budget. Entire batches roll back on validation, conflict, rate-limit or storage failure. Counter state uses no IP/customer identity. Empty/invalid JSON and payloads are permanent 400 errors; conflicting identity is 409; oversized body 413; wrong content type 415; throttling 429 with Retry-After; storage outage 503 with a retryable safe error. No raw database/provider/checkout payload enters the response or logs.

CORS permits public origins without credentials. Public IDs and CORS are not cryptographic authentication; browser events can be forged. Reports must continue labelling browser-observed data accordingly. Platform/WAF ingress protection, production retention, production pixel delivery/retry, purchase normalisation and report aggregation remain their respective tickets.

`test:ingestion` applies all migrations to a fresh isolated schema and checks durable acknowledgement, concurrent deduplication, custom retry identity, unknown references, ended-revision delivery, out-of-order rendering, schema/PII/value/timestamp rejection, atomic rate-limit rollback, cross-process-safe counters, oversized bodies and retryable database outage. Actual Next route checks also cover invalid versions, CORS and oversized requests. No live provider surface is asserted by those fixtures.
